## 12.1 引言

程序员经常持续寻找问题的“更优解”，例如更高的性能、更好的可维护性或更好的易用性。只有真正实现某种方案之后，才能理解它附带的各种细节，而这些细节往往会成为最终选择方案的决定因素。

在 AI 开发中，一个常见问题是行为选择。有限状态机、行为树、效用选择、神经网络和规划器都可以用于解决这个问题。文章通过开发过程中可能遇到的实际案例，讨论一种称为分层任务网络（Hierarchical Task Network，HTN）的规划器及其实现细节。

包括 HTN 在内的规划架构接收一个问题，并输出一系列能够解决该问题的步骤。在 HTN 中，这组步骤称为计划。HTN 与其他规划器的区别在于：它允许使用一个非常高层的任务表示问题，然后在规划过程中递归地把该任务分解成更小的任务。分解完成后，最终得到一系列不可再分的原子任务，它们共同组成计划。

把高层任务分解成较小任务，是解决许多问题时很自然的方法。本文中的问题就是“确定接下来该做什么”。HTN 具有较高的模块化程度和较快的运行时执行速度，因此是一种有吸引力的行为选择方案。这些优点与行为树有相似之处，但 HTN 规划器还能推理候选行动产生的效果。对未来进行推理的能力，使 HTN 能够以很强的表达能力描述行为。

HTN 规划存在多种不同系统。本文讨论的是《变形金刚：赛博坦的陨落》中使用的系统，它以总序前向分解规划器为基础。文章通过一个经过简化的虚构案例，说明开发中遇到的挑战以及采用 HTN 后得到的收益。

示例 NPC 是一个名为 Trunk Thumper 的巨魔。设计师最初对它的描述是：一个巨大、凶恶、行动迟缓的巨魔；它会巡逻自己的多座桥梁，并使用一根大树干攻击经过的敌人。文章随后像真实开发过程一样，不断修改这一设计。

## 12.2 HTN 的构成要素

在构建 Trunk Thumper 的行为之前，文章先介绍 HTN 的基本构成。

NPC 在本文中就是 Trunk Thumper。它拥有一个规划器，规划器使用领域和世界状态构造一组任务，这组任务称为计划。计划由 NPC 的计划执行器运行。NPC 的传感器以及计划执行器成功完成的任务都会更新世界状态。

图 12.1 展示的系统关系如下：

```text
传感器 ──更新──> 世界状态
                  │
                  v
HTN 领域 ──> 规划器 ──生成──> 计划 ──> 计划执行器
                                      │
                                      └──成功任务的效果──> 世界状态
```

### 12.2.1 世界状态

与其他行为算法一样，HTN 需要一种描述当前问题空间的知识表示。对 Trunk Thumper 来说，它需要描述巨魔对于外部世界和自身状态的认识。

其他行为算法可能直接查询游戏对象的实际状态，例如位置或生命值。HTN 则要求把这些信息编码为它能够理解的形式，这种形式称为世界状态。世界状态本质上是一组属性构成的向量，用来描述 HTN 需要推理的内容。

原文用伪代码说明，世界状态可以是一个由枚举索引的字节数组或向量：

- `EHtnWorldStateProperties` 定义属性索引，例如 `WsEnemyRange`、`WsHealth`、`WsIsTired`。
- 每个属性可以拥有自己的取值集合。
- `WsIsTired` 可以用字节值 0 和 1 表示布尔状态。
- `WsEnemyRange` 可以使用 `EEnemyRange` 中的 `MeleeRange`、`ViewRange`、`OutOfRange` 等枚举值。

世界状态只需要表示 HTN 进行决策所需的信息。正因为如此，`WsEnemyRange` 使用“近战范围”“视野范围”“范围之外”等抽象值，而不是实际距离。

世界状态的目标不是表示游戏中每个对象的全部可能状态，而是表示规划器作出决策所需的问题空间。在示例中，它只需要包含 Trunk Thumper 作出决策所需的状态。

### 12.2.2 传感器

HTN 输出的是由任务组成的计划，任务执行后会影响世界状态。但是玩家、其他 NPC 等外部因素也会改变世界状态。

例如，敌人与巨魔都能影响 `WsEnemyRange`：

- 巨魔执行移动任务时，可以由任务更新该属性。
- 敌人自行移动造成的距离变化，不属于 HTN 任务执行的结果，规划器自身不会处理这种变化。

外部变化可以通过多种方式转换为世界状态。文章推荐使用一个简单的传感器系统，管理一组采用时间分片更新的传感器。不同传感器分别管理不同的世界状态属性，例如视觉、听觉、距离和生命传感器。

这些传感器的工作方式与其他 AI 系统中的传感器相同，只是多出一步：把感知结果编码为 HTN 能够理解的世界状态。

### 12.2.3 原子任务

HTN 由任务组成。用于构建 HTN 的任务有两类：复合任务与原子任务。

原子任务代表 NPC 可以执行的一个独立步骤。例如：

- 从地里拔出一棵树。
- 使用树干发动一次重击。

HTN 最终生成的计划就是一组原子任务。一个原子任务由以下内容构成：

- 一个 Operator。
- 一组 Effect。
- 一组 Condition。

原子任务要执行，其条件集合必须有效。条件使任务实现者能够保证任务只在正确状态下运行。

原子任务条件并不是 HTN 实现的必要组成，但文章建议使用它们。这样可以减少 HTN 更高层级中重复进行同类检查，也可以避免在多个位置重复检查条件而引入潜在错误。

Effect 描述任务成功完成后如何改变 NPC 的世界状态。例如 `DoTrunkSlam` 会执行树干近战攻击，并使巨魔进入疲劳状态。这个任务的 Effect 就负责描述“变得疲劳”的结果。

由于结果以 Effect 的形式明确表示，HTN 能够推理未来状态。Trunk Thumper 因而可以判断在 `DoTrunkSlam` 之后应该做什么，甚至可以判断是否值得执行该任务。

Operator 表示 NPC 能够执行的一个原子动作。它听起来与原子任务本身相似，但区别在于：原子任务通过自身的条件和效果，解释 Operator 在当前 HTN 领域中的含义。

原文使用 `SprintToEnemy` 与 `WalkToNextBridge` 说明这一点：

- 两个任务都可以使用同一个 `MoveTo` Operator。
- `SprintToEnemy` 成功后，NPC 位于敌人身边并变得疲劳。
- `WalkToNextBridge` 成功后，NPC 位于桥边，并且无聊程度增加。

同一个移动 Operator 因此可以在任务网络中表达两种不同用途。

原文给出的原子任务表示形式包括任务名、可选前置条件、Operator 和可选 Effect。两个示例如下：

| 任务 | 前置条件 | Operator | Effect |
| --- | --- | --- | --- |
| `SprintToEnemy` | `WsHasEnemy == true` | 快速导航到敌人位置 | 位置变为敌人位置，并进入疲劳状态 |
| `WalkToNextBridge` | 无 | 缓慢导航到桥的位置 | 位置变为桥的位置，无聊程度加一 |

### 12.2.4 复合任务

复合任务体现了 HTN 的层级性质。可以把复合任务看作一个存在多种完成方式的高层任务。

例如，Trunk Thumper 可能拥有 `AttackEnemy` 任务：

- 如果拥有树干，可以跑向目标，把树干当作近战武器攻击敌人。
- 如果没有树干，可以从地面拔出巨石并投向敌人。
- 在条件合适时，还可以存在更多攻击方式。

为了确定采用哪一种方式完成复合任务，需要选择合适的 Method。Method 由一组 Condition 和一组 Task 构成：

- Condition 与当前世界状态进行验证，用来判断这个 Method 是否可选。
- Task 集合也称为 Subtask，表示该 Method 的具体做法。
- Subtask 可以同时包含原子任务和复合任务。

复合任务能够出现在其他复合任务的 Method 中，这正是分层任务网络产生层级结构的方式。

`AttackEnemy` 的两个 Method 可以整理为：

| Method | Condition | Subtask |
| --- | --- | --- |
| 使用树干近战 | `WsHasTreeTrunk == true` | 导航到敌人，然后执行树干重击 |
| 投掷巨石 | `WsHasTreeTrunk == false` | 从地面抬起巨石，然后投向敌人位置 |

理解复合任务后，就可以构造一个很大的任务层级：最上层可能是 `BeTrunkThumper`，它被分解为若干较小任务，这些任务继续被分解，直到得到原子任务。

复合任务本质上只是多个 Method 的容器，每个 Method 代表一种完成高层任务的方法。在计划执行阶段不会运行复合任务代码，真正被执行的是最终计划中的原子任务 Operator。

## 12.3 构建 HTN 领域

领域（Domain）是整个任务层级的总称。文章为 Trunk Thumper 构建了一个简单领域。

根复合任务叫作 `BeTrunkThumper`，用于概括“成为 Trunk Thumper 意味着什么”。它包含两个按顺序排列的 Method：

| 优先顺序 | Condition | Subtask |
| --- | --- | --- |
| 第一 Method | 能看见敌人 | 导航到敌人，然后执行树干重击 |
| 第二 Method | 始终成立 | 选择下一座桥，导航到桥，然后检查桥 |

第一个 Method 定义巨魔的最高优先级。如果它能看见敌人，就通过 `NavigateToEnemy` 接近敌人，再通过 `DoTrunkSlam` 发起攻击。如果条件不成立，则尝试下一个 Method，依次选择桥、前往桥并检查桥上是否有敌人。

这些 Method 使用的原子任务包括：

| 原子任务 | Operator | Effect |
| --- | --- | --- |
| `DoTrunkSlam` | 执行指定名称的攻击动画 | 无 |
| `NavigateToEnemy` | 导航到敌人位置引用 | `WsLocation` 变为敌人位置 |
| `ChooseBridgeToCheck` | 选择要检查的桥 | 无 |
| `NavigateToBridge` | 导航到下一座桥的位置引用 | `WsLocation` 变为下一座桥的位置 |
| `CheckBridge` | 播放搜索动画并检查桥 | 无 |

`DoTrunkSlam` 说明原子任务如何在 HTN 领域中解释 Operator。它实际执行的是一个动画攻击 Operator，并把动画名作为参数传入。

`NavigateToEnemy` 也体现了同一原则；它成功后，还会通过 Effect 把世界状态 `WsLocation` 设置为敌人位置引用。

## 12.4 寻找计划

领域由复合任务和原子任务构成。规划器结合领域与世界状态生成计划，是 HTN 的核心部分。

以下三种情况会迫使规划器寻找新计划：

1. NPC 完成或执行失败当前计划。
2. NPC 当前没有计划。
3. 传感器改变了 NPC 的世界状态。

出现任意一种情况，规划器就尝试生成计划。

规划从表示问题领域的根复合任务开始。在示例中，根任务是 `BeTrunkThumper`。规划器首先：

1. 把根任务压入 `TasksToProcess` 栈。
2. 复制当前世界状态，得到 Working World State。
3. 在后续规划过程中修改这份工作状态，以模拟任务执行后可能发生的事情。

之后，规划器循环处理 `TasksToProcess`：

### 处理复合任务

1. 从栈顶弹出任务。
2. 如果它是复合任务，按 Method 顺序搜索第一组条件成立的 Method。
3. 找到有效 Method 后，记录本次分解状态。
4. 把该 Method 的 Subtask 加到 `TasksToProcess` 栈顶。
5. 如果没有找到有效 Method，恢复到上一个已经分解的复合任务处。

### 处理原子任务

1. 检查原子任务的前置条件是否满足当前工作世界状态。
2. 条件满足时，把任务加入最终计划。
3. 把任务的 Effect 应用到工作世界状态。
4. 条件不满足时，同样恢复到上一个已经分解的复合任务处。

应用 Effect 的原因是规划器假定加入计划的任务将成功执行。后续 Method 和原子任务便可以基于模拟后的未来状态作出判断。

循环一直持续到 `TasksToProcess` 为空。完成后，规划器要么得到一组原子任务，要么回退到无法再继续的位置并返回“没有计划”。

文章中的规划逻辑可以概括为：

```text
复制当前世界状态为工作状态
把根任务压入待处理栈

当待处理栈不为空：
    弹出当前任务
    如果是复合任务：
        查找第一个条件满足的 Method
        找到：保存规划现场，把 Subtask 压入待处理栈
        找不到：恢复上一个分解现场
    如果是原子任务：
        条件满足：应用 Effect，并加入最终计划
        条件不满足：恢复上一个分解现场
```

`RecordDecompositionOfTask` 和 `RestoreToLastDecomposedTask` 负责记录与恢复规划器状态。

记录函数把规划现场压入 `DecompHistory` 栈，记录内容包括：

- `TasksToProcess` 容器。
- `FinalPlan` 容器。
- 本次分解选择的 Method。
- 拥有该 Method 的复合任务。

当复合任务无法分解，或者原子任务条件不满足时，恢复函数弹出记录的现场，使规划器能够回溯并尝试其他分支。

规划器使用深度优先搜索寻找有效计划，因此在最坏情况下可能需要搜索完整领域。不过它遍历的是任务层级，复合任务的 Method 可以一次排除任务网络中的大块区域。

该实现不使用 A* 或 Dijkstra 那样的启发式或 Cost，因此不需要排序。文章指出，这些特性使《变形金刚：赛博坦的陨落》中的 HTN 规划器明显快于《变形金刚：赛博坦之战》中使用的 GOAP 系统。

图 12.2 展示了一个扩展后的分解案例：

- 根任务仍是 `BeTrunkThumper`。
- `DoTrunkSlam` 变成了复合任务，并拥有两个不同版本的树干重击 Method。
- 示例选择 `BeTrunkThumper.Method0` 和 `DoTrunkSlam.Method1`。
- 分解从根任务开始，把 `NavToEnemy`、`DoTrunkSlam`、`Recover` 放入待处理序列。
- `DoTrunkSlam` 再分解为 `Tell` 与 `Slam`。
- 最终计划为 `NavToEnemy → Tell → Slam → Recover`。

## 12.5 运行计划

HTN 计划的运行过程比较直接。NPC 的计划执行器按顺序执行每个原子任务的 Operator。

- 每个任务成功完成后，把该任务的 Effect 应用到实际世界状态。
- 如果 Operator 因自身执行原因返回失败，整个计划失败并触发重新规划。
- 如果当前任务或任意剩余任务的条件变为无效，计划也会失败。

为了检查整个剩余计划，计划执行器维护一份与规划器类似的工作世界状态。它依次验证任务的前置条件，并在验证通过后把任务 Effect 应用到工作状态。后续任务的前置条件可能依赖这些 Effect，因此验证过程中必须应用它们。

这种计划验证机制增强了 HTN 领域的表达能力，也使计划能够对世界状态变化作出反应。

## 12.6 使用递归增强表达能力

设计师看到游戏中的巨魔后，认为树干攻击过强，于是要求树干在攻击三次后损坏，迫使巨魔寻找一根新树干。

首先在世界状态中加入 `WsTrunkHealth`。然后把攻击行为包装进新的复合任务 `AttackEnemy`，并通过递归修改行为。

新的领域结构为：

### 根任务 `BeTrunkThumper`

- 能看见敌人时，执行新的复合任务 `AttackEnemy`。
- 否则继续选择桥、前往桥并检查桥。

### 复合任务 `AttackEnemy`

| Method | Condition | Subtask |
| --- | --- | --- |
| 正常攻击 | 树干耐久大于 0 | 导航到敌人，然后执行树干重击 |
| 获取新树干 | 始终成立 | 找树、前往树的位置、拔出树干，然后再次执行 `AttackEnemy` |

相关原子任务的状态变化为：

- `DoTrunkSlam` 每次成功后令 `WsTrunkHealth` 减一。
- `UprootTrunk` 成功后把 `WsTrunkHealth` 设为三。
- `NavigateToTrunk` 成功后把 `WsLocation` 设置为找到的树的位置。

当巨魔能看见敌人时，它仍会像以前一样攻击，只是现在通过 `AttackEnemy` 复合任务完成。如果树干仍有耐久，选择高优先级 Method；连续攻击会逐步降低耐久，树干损坏后便落到较低优先级的获取树干 Method。

获取树干 Method 最后再次调用 `AttackEnemy`，形成递归。如果此时树干耐久仍为零，规划器会陷入无限循环。但 `UprootTrunk` 的 Effect 已经把耐久恢复为三，因此再次分解 `AttackEnemy` 时可以选择正常攻击 Method。

最终计划可以是：

```text
FindTrunk → NavigateToTrunk → UprootTrunk → NavigateToEnemy → DoTrunkSlam
```

这种领域结构复用了已有 Method，使巨魔在获得新树干后重新回到攻击行为。

## 12.7 为不受任务控制的世界状态变化进行规划

此前计划主要依赖原子任务的 Effect 改变世界状态。本节讨论由原子任务之外的因素改变世界状态时如何规划。

设计师注意到：巨魔看不见敌人后会直接恢复巡桥。他希望巨魔追到最后一次看到敌人的位置，并在重新发现敌人后作出反应。

根任务增加一个位于攻击与巡逻之间的新 Method：

| Condition | Subtask |
| --- | --- |
| 能看见敌人 | 攻击敌人 |
| 最近看见过敌人 | 前往最后看到敌人的位置，然后执行重新获得视线后的咆哮 |
| 始终成立 | 巡逻桥梁 |

`NavToLastEnemyLoc` 导航到敌人最后出现的位置，并把 `WsLocation` 设置为该位置。`RegainLOSRoar` 的前置条件是 `WsCanSeeEnemy == true`。

问题在于 `WsCanSeeEnemy` 由视觉传感器管理。规划器尝试把 `RegainLOSRoar` 加入最终计划时，它的前置条件尚未成立，因为领域中没有任何信息表示完成导航后预期会重新看到敌人。

文章为此引入 Expected Effect：

- Expected Effect 只在规划和计划验证阶段应用。
- 它用于表达执行某些任务后预期会发生的世界状态变化。
- 规划器可以基于途中预期达成的状态，继续向更远的未来规划。

修改后的 `NavToLastEnemyLoc` 同时拥有：

- 普通 Effect：位置变为敌人最后出现的位置。
- Expected Effect：预期 `WsCanSeeEnemy` 变为 `true`。

当任务在分解过程中被处理时，Expected Effect 会更新工作世界状态，因此 `RegainLOSRoar` 的前置条件可以通过，规划器也能够继续生成完整任务链。

文章说明，这个行为也可以用其他方式实现，但 Expected Effect 在《变形金刚：赛博坦的陨落》的开发中多次发挥作用，它能以简单方式增强 HTN 领域的表达能力。

## 12.8 如何处理更高优先级的计划

此前复合任务按照 Method 的排列顺序进行分解，这是一种自然的搜索方式。本节通过修改攻击行为讨论计划优先级。

修改后的 `AttackEnemy` 拥有三个 Method：

| 优先顺序 | Condition | Subtask |
| --- | --- | --- |
| 高 | 树干未损坏、最近没有攻击、能够导航到敌人 | 前往敌人、树干重击、恢复咆哮 |
| 中 | 树干损坏 | 找树、前往树的位置、拔出树干、递归攻击 |
| 低 | 始终成立 | 拾取巨石并投掷 |

`DoTrunkSlam` 成功后减少树干耐久，并把 `AttackedRecently` 设为 `true`。设计变更的原因包括：

- 巨魔持续攻击，对玩家压力过大，因此重击后加入恢复动画。
- 最近攻击过时，不允许立刻再次重击。
- 巨魔因障碍等原因无法到达敌人时，改用低优先级的投石攻击。

问题会发生在重击之后执行 `RecoveryRoar` 时。如果世界状态变化触发重新规划，刚完成的 `DoTrunkSlam` 已经把 `AttackedRecently` 设为 `true`。规划器重新分解时会跳过树干重击 Method，落到投石 Method，于是仍然有效的 `RecoveryRoar` 会在执行途中被取消。

这说明系统需要识别正在运行计划的优先级。

一种方案是把 HTN 看作图，并使用 A* 或 Dijkstra 等基于 Cost 的搜索。可以给任务或 Method 绑定 Cost，但文章指出：

- 实际调整这些 Cost 比较困难。
- 规划器需要增加排序，降低执行速度。

文章希望保留 Method“按排列顺序表示优先级”的简洁性和可读性。困难在于：计划只包含原子任务及其 Operator，并不知道规划器通过哪些复合任务和 Method 得到它。

解决方法是记录规划器搜索领域时经过的路径，称为 Method Traversal Record（MTR）。MTR 保存为了生成计划，每个被分解复合任务最终选择的 Method 索引。

图 12.3 给出的计划及 MTR 为：

| MTR | 计划 | 相对优先级 |
| --- | --- | --- |
| `0, 0` | `NavToEnemy → Taunt → SuperSlam → Recover` | 最高 |
| `0, 1` | `NavToEnemy → Tell → Slam → Recover` | 次高 |
| `1` | `ChooseBridge → NavToBridge → CheckBridge` | 最低 |

MTR 有两种使用方式：

1. 正常生成新计划，再比较新计划与当前计划的 MTR。如果新计划选择的所有 Method 索引都具有相同或更高优先级，就接受新计划。
2. 在新一轮分解过程中直接使用当前计划的 MTR，只允许选择优先级相同或更高的 Method。这样能够根据当前 MTR 提前排除 HTN 的完整分支。

第一种方式更容易实现；如果规划器消耗了大量处理时间，第二种方式可以帮助提升速度。

### 任务 Effect 引发重规划的问题

支持高优先级计划中断当前计划后，还存在一个可能产生意外行为的实现细节。如果所有世界状态变化都会触发重新规划，那么任务成功执行并应用 Effect 时也会触发重新规划。

文章修改攻击领域，实现“执行三次树干重击后使用旋风攻击”：

- `DoTrunkSlam` 每次成功使 `WsPowerUp` 加一。
- 当 `WsPowerUp == 3` 时，高优先级 Method 选择 `DoWhirlwindTrunkAttack`，然后执行恢复。
- 普通 Method 执行 `DoTrunkSlam`，然后执行恢复。
- 旋风攻击完成后把 `WsPowerUp` 重置为零。

第三次 `DoTrunkSlam` 完成后，Effect 把 `WsPowerUp` 变为三并触发重新规划。规划器立即选择更高优先级的旋风攻击，于是取消了用于分隔两次攻击、给玩家反应时间的 `DoRecovery`。表现结果就是巨魔每次都会从第三次树干重击直接连到旋风攻击。

一种简单处理方式是：原子任务成功后应用 Effect 时，不因为这些 Effect 触发重新规划。规划阶段已经考虑过这些状态变化，因此这样做是合理的。但这仍不是完整解决方案，因为任务之外的任意世界状态变化仍可能触发重规划，使问题再次出现。

文章指出，根本问题在于领域没有正确表示行为原因。

可以把恢复动画合并到攻击动画中，保证重击后一定播放恢复。但这会降低领域模块化程度，也难以支持“连续执行三次重击后再恢复”等变化。

文章采用的改法是增加 `WsIsTired`：

- `DoTrunkSlam` 除了增加 `WsPowerUp`，还把 `WsIsTired` 设为 `true`。
- `DoWhirlwindTrunkAttack` 增加前置条件 `WsIsTired == false`。
- `DoRecovery` 完成后把 `WsIsTired` 设为 `false`。

这样就明确表示了为什么需要恢复。世界状态发生变化并触发重新规划时，巨魔仍然无法在疲劳状态执行旋风攻击，因此 `DoRecovery` 不会被中断，同时 `DoTrunkSlam` 和 `DoRecovery` 仍保持模块化。

文章强调，实现计划优先级时，这类细节可能使 NPC 出现难以预料的行为。遇到这类问题时，需要检查世界状态是否正确表示了现实原因；该案例只需增加一个简单的世界状态就能解决。

## 12.9 管理同时发生的行为

许多行为选择算法擅长一次执行一件事，但同时执行两个行为时会变得复杂。文章介绍了 HTN 中处理这一问题的几种方式。

### 把多个 Operator 合并为一个

最直接的想法是把多个 Operator 合并成一个。这样可以工作，但存在以下问题：

- 无法复用已经开发的 Operator。
- 多个 Operator 合并后复杂度增加，可维护性下降。
- 组合行为出现变化时，如果处理不当，可能产生重复代码。

同时行为会经常出现，因此文章建议避免这种方式。

### 使用多个领域和多个规划器

一种更直观的方式，是针对 NPC 的不同身体部分构建不同 HTN 领域。

例如，巨魔需要一边接近敌人，一边防御远程攻击。可以把行为拆成：

- 控制下半身的导航 Operator。
- 控制上半身的防御 Operator。

然后分别为上半身和下半身构建两个领域并使用两个规划器。

上半身领域可以按以下顺序决策：

1. 有敌人且敌人在近战范围内时，执行树干重击。
2. 正在导航且受到远程攻击时，用手臂保护脸部。
3. 其他情况执行 Idle。

下半身领域可以按以下顺序决策：

1. 有敌人且敌人在近战范围之外时，导航到敌人，然后递归执行下半身根任务。
2. 其他情况执行 Idle。

使用多个规划器时，需要同步各自的任务。可以通过世界状态描述每个规划器正在做什么。例如，任何下半身导航任务运行时，把 `Navigating` 设为 `true`，上半身规划器便可以据此进行决策。

文章指出，这种方案可以正常工作，但有几个问题：

- 第二个规划器会增加一定性能开销。
- 保持两个领域同步会降低可维护性。
- 多规划器会显著增加调试难度。

### 把持续过程放到后台

文章还提出一种只使用一个规划器的方案。

原本导航任务会在到达目的地后才结束。可以改为：导航任务只负责启动路径跟随，然后立即完成；路径跟随在后台持续进行，不作为计划执行器中的当前任务。

这样规划器可以在导航期间继续选择其他行为，包括抬起手臂抵挡攻击。该方案要求世界状态表示：

- 当前是否正在导航。
- 当前距离目的地多远。

领域按以下顺序决策：

1. 有敌人且敌人在近战范围内时，执行树干重击。
2. 有敌人且敌人在近战范围之外时，启动导航到敌人的任务。
3. 正在导航且受到远程攻击时，用手臂保护脸部。
4. 其他情况执行 Idle。

`NavigateToEnemy` 启动后台导航，并通过 Effect 把 `Navigating` 设为 `true`。

这种单领域方案与双领域方案依赖同样的世界状态：

- 双领域方案用 `Navigating` 同步两个规划器。
- 单领域方案用世界状态表示后台正在发生的路径跟随过程。

后者不需要同时运行两个领域和两个规划器。

## 12.10 使用部分计划加快规划速度

假设 Trunk Thumper 的领域已经成长为一个很大的任务网络，并且在优化规划器本身之后，仍需要减少几毫秒规划时间。

HTN 会通过复合任务的 Method 自然排除大量搜索空间。有时可以增加更多 Method，进一步排除搜索分支，但前提是拥有合适的世界状态表示。

如果这些方法仍无法满足性能要求，可以使用部分规划。文章把部分规划称为 HTN 最强大的能力之一。

部分规划允许规划器不把完整计划全部分解完成。HTN 能做到这一点，是因为它使用前向分解或前向搜索：规划器从当前世界状态出发，沿时间向未来规划，因此可以只向前规划几个步骤。

相对而言，GOAP 和 STRIPS 的一些变体使用反向搜索，从目标状态向当前世界状态搜索。反向搜索必须完成整个搜索，才能知道第一步应该做什么。

### 手动拆分部分计划

文章先使用简化领域说明：当 `WsCanSeeEnemy == true` 时，一个 Method 同时展开 `NavigateToEnemy` 和 `DoTrunkSlam`。

由于导航任务可能执行很长时间，因此很适合拆成部分计划。继续对很远的未来进行规划意义不大，因为导航期间世界状态很可能变化，迫使巨魔作出不同决策。

原来的一个 Method 被拆为两个：

| 优先顺序 | Condition | Subtask |
| --- | --- | --- |
| 高 | 能看见敌人，并且敌人在近战范围之外 | 仅执行 `NavigateToEnemy` |
| 低 | 能看见敌人 | 执行 `DoTrunkSlam` |

如果巨魔在近战范围外，就只规划导航部分。导航完成后再次规划，此时不再满足第一个 Method，转而选择树干重击。

导航任务通常耗时较长，因此是部分计划的主要候选。文章特别指出：只有存在能够区分拆分点的世界状态时，才能这样拆分计划。

### 自动按时间拆分的风险

手动部分规划需要领域作者主动设计拆分点。也可以给原子任务赋予“时间”概念，让规划器记录已经规划到未来多远，并在超过阈值时自动截断。

文章通过 `DoTrunkSlam` 需要 `WsStamina > 0` 的例子说明自动截断的问题。

假设构成导航的原子任务已经超过规划器的时间阈值，规划器会只让巨魔开始接近敌人。如果此时 `WsStamina == 0`，后面的 `DoTrunkSlam` 实际无法满足前置条件。自动截断使规划器没有机会验证计划后半部分，因此可能执行本不应该执行的前半部分。

可以把体力条件上移到 Method 中避免问题，但 Method 检查和原子任务前置条件检查本来都属于有效写法。为了保证两种写法产生相同结果，自动部分规划需要处理这一差异，否则会引入隐蔽错误。

### 从部分计划的中断点继续

另一个问题是如何从部分计划停止的位置继续。

可以重新从根任务规划，但这样必须修改领域，使它能够识别完整计划的第一部分已经完成。以示例来说，需要加入一个更高优先级 Method，检查巨魔是否已经进入近战范围。如果仍然需要手工增加这种 Method，自动部分规划的意义就会减弱。

更好的方案是保存尚未处理的任务列表状态，并让规划器支持从一组任务开始，而不仅仅从一个根任务开始。这样能够从上次停止的位置继续搜索。

不过第二部分规划无法回退到第一部分开始之前。如果第二部分后来验证失败，就表示 NPC 已经执行了原本不应该执行的任务。存在这种情况时，说明计划后面的任务必须提前验证才能得到正确行为，因此不能使用部分规划。

在《变形金刚：赛博坦的陨落》中，团队选择把部分计划直接设计进领域。原因包括：

- 自动拆分引入隐蔽错误的可能性较高。
- 在不需要验证完整计划时，开发者本来就会自然地在 NPC 领域中构造部分计划。
- 12.9 节最后介绍的后台导航方案，本身也是部分规划的一个例子，游戏中的许多 NPC 都使用了类似方案。

## 12.11 结论

即使只是创建一个简单 NPC，完整经历这一过程也能揭示行为选择系统实现中的许多细节。

文章通过 Trunk Thumper 示例展示了：

- HTN 以自然方式描述行为。
- 原子任务具有复用性和模块化特征。
- HTN 能推理未来状态，因此拥有规划器特有的表达能力。
- 实现 HTN 时会遇到世界状态表示、任务回退、计划优先级、同时行为和部分规划等潜在问题。

HTN 为《变形金刚：赛博坦的陨落》的 AI 程序员带来了实际收益。作者最后表示，相信它也能为其他开发者带来同样的帮助。
